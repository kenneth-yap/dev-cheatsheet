⚠️ Mistake recovery
Committed to the wrong branch

Method A — Move commits to a new branch (safest):

bash
git checkout -b feat/my-feature    # create the correct branch HERE (has your commits)
git checkout main
git reset --hard origin/main       # remove wrong commits from main

Method B — Cherry-pick to an existing branch (move one specific commit):

bash
git log --oneline                  # find the commit hash, e.g. abc1234
git checkout feat/existing-branch
git cherry-pick abc1234            # copies that commit here

git checkout main
git reset --hard origin/main       # remove from main
Before any reset Run git status first. If there are uncommitted changes, stash them with git stash push -u -m "my-wip" before resetting.
Undoing commits — 3 levels
CommandKeeps files?Keeps staging?Use when
git reset --soft HEAD~1Yes ✓Yes ✓Rewrite the commit message or combine commits
git reset HEAD~1Yes ✓No ✗Re-stage and recommit differently (most common)

git revert abc1234    # creates a NEW commit that undoes abc1234 — safe to push
git push
Stashing safely
Never use bare git stash pop in multi-session or worktree projects — you could pop someone else's stash. Always tag your stash.
bash
git stash push -u -m "my-unique-description"   # -u includes untracked files
git stash list
# stash@{0}: On main: my-unique-description

git stash apply stash@{0}    # restore — NOT pop (keeps the stash safe)
git stash drop stash@{0}     # drop manually when done

Preferred alternative: make a WIP commit and reset it later:

bash
git add path/to/work
git commit -m "wip: in progress — do not merge"
# switch branches, do other things...
git reset HEAD~1              # undo the WIP commit, keep your file changes
Cherry-pick — copy a specific commit to another branch
Used in this project to move library_search.py from a wrong branch to a clean one
bash
git log --oneline             # find the commit hash you want to copy
# e.g. d293d46 fix: rollback broken transaction before lexical fallback

git checkout feat/clean-branch
git cherry-pick d293d46       # copies just that commit onto this branch

# If there's a conflict during cherry-pick:
# fix the conflict, then:
git add the-file.py
git cherry-pick --continue    # or: git cherry-pick --abort to cancel

When to use vs rebase: cherry-pick copies one or a few specific commits. Rebase replays an entire branch. For "I made this commit in the wrong place and want it here", cherry-pick is the right tool.

  2. Find the first FAILED or ERROR line (not the summary at the bottom)
  3. Group all failures by error type before touching any code. 14 test failures → 4 root causes → 4 fixes (not 14)

When production code changes — what to update in tests
4 patterns to grep for when a function's return type, shape, or arguments change

When you change a function (return type, rename a field, change arguments), tests break in predictable ways. Search for these 4 patterns before running CI:

Pattern to search forWhy it breaksFix
list(fn())If fn is now async, list() wraps the coroutine object — you get a list with one coroutine, not the itemsChange to await fn() or [x async for x in fn()]

grep -rn "list(search_shelf" tests/        # 1. list() wrapping async gen
grep -rn "\"embedding\" in " tests/       # 2. old field name
grep -rn "assert result ==" tests/        # 3. exact dict equality
grep -rn "assert_called_with" tests/      # 4. call argument assertions
Pushing after a PR is merged — the commit is invisible on that PR and on main
Merged PR is frozen. After a PR merges, GitHub freezes its commit list. Any new push to the same branch appears nowhere useful — not on the closed PR, not on main.
❌ Push to merged branch — invisible
# PR #43 already merged into main
git add .
git commit -m "fix: add missing guard"
git push origin fix/ruff-billing-unused-import
# → commit exists on GitHub but is not in main
# → not shown on PR #43 (closed)
# → your reviewer "cannot see the commit"
✓ New PR for follow-up work
# After PR #43 merged, start fresh from main
git fetch origin main
git checkout -B fix/ruff-billing-unused-import origin/main
git add .
git commit -m "fix: add missing guard"
git push -u origin fix/ruff-billing-unused-import
# → open a NEW PR — this is PR #44, not #43

Confirm with git log origin/main..HEAD — if your commit doesn't appear there, it's not in main. Do not look at the closed PR's commit list or the merge commit SHA.

Files saved inside a container are deleted on every redeploy
Critical architecture finding — affects any uploaded file storage
Container filesystem is ephemeral. Every Elestio redeploy creates a fresh container from the image. Any files written to the container's local disk (e.g. storage_root, uploaded documents) are permanently deleted. This is a silent data loss bug — no error, the files just vanish.
❌ Before — files lost on every deploy
# config.py
storage_root = "storage/"   # relative path
                             # → inside the container
                             # → deleted every redeploy
# docker-compose.yml — no volumes
services:
  backend:
    image: scribtive-backend
    # files written to /app/storage/
    # are gone after every redeploy
✓ After — Option A: Docker named volume
# docker-compose.yml
services:
  backend:
    image: scribtive-backend
    volumes:
      - uploads:/app/storage   # ← persist outside container

volumes:
  uploads:   # named volume survives redeploys
# config.py
storage_root = "/app/storage"  # absolute path
                                # → mapped to named volume
FixHowWhen to use
Docker named volumeAdd volumes: - uploads:/app/storage to docker-compose.ymlSimple; data lives on the host machine
Supabase StorageStore files via Supabase Storage API; only store the reference URL in DBProduction-grade; survives any redeploy; CDN delivery

Rule of thumb: If a file needs to survive a deployment, it must live outside the container — in a volume or an external storage service.

Advisory locks — prevent concurrent migration runs
The fix for the Elestio boot crash
The production bug: Elestio runs multiple app instances for reliability. On deploy, all instances start simultaneously and all call alembic upgrade head at the same time. Two processes modifying the same DB tables → race condition → app crashes on every deploy.
❌ Before — all instances race
# docker-entrypoint.sh (simplified)
# This runs on EVERY instance simultaneously
subprocess.run(
    ["alembic", "upgrade", "head"],
    check=True
)
# Instance 1, 2, 3 all run this at once
# → conflict modifying same tables
# → app crashes on boot
✓ After — serialised with advisory lock
conn = psycopg2.connect(url)
conn.autocommit = True
cur = conn.cursor()

# Instances 2 + 3 BLOCK here until
# instance 1 releases the lock
cur.execute("SELECT pg_advisory_lock(42)")
try:
    subprocess.run(
        ["alembic", "upgrade", "head"],
        check=True
    )
finally:
    cur.execute("SELECT pg_advisory_unlock(42)")
    conn.close()
  • The number 42 is arbitrary — just needs to match across all instances
  • Use a direct connection (not the pooler) — pooler doesn't preserve session locks
  • finally block ensures the lock is released even if alembic crashes
  • In Scribtive OS this runs in docker-entrypoint.sh before the app starts

SQLAlchemy — parameterized queries
Safe queries — always use parameters, never f-strings for user data
❌ SQL injection risk
rows = session.execute(text(
    f"SELECT * FROM docs WHERE shelf = '{shelf}'"
    # shelf = "x'; DROP TABLE docs; --"
))
✓ Safe — parameterized
rows = session.execute(
    text("SELECT * FROM docs WHERE shelf = :shelf"),
    {"shelf": shelf}   # shell content never touches SQL
)
python — the full pattern from library_search.py
from sqlalchemy import text
from sqlalchemy.orm import Session

def search_shelf(session: Session, shelf: str, query: str, k: int = 5) -> list[dict]:
    # Vector as a string literal is OK — it's computed from embed_texts, not user input
    qv = embed_texts([query])[0]
    vec_str = "[" + ",".join(str(x) for x in qv) + "]"

    rows = session.execute(
        text("""
            SELECT lp.doc_id, ld.title, lp.page, lp.text,
                   1 - (lp.embedding_vec <=> CAST(:vec AS vector)) AS vec_sim
            FROM library_pages lp JOIN library_docs ld ON ld.id = lp.doc_id
            WHERE ld.shelf = :shelf AND ld.status = 'ready'
            ORDER BY lp.embedding_vec <=> CAST(:vec AS vector)
            LIMIT :limit
        """),
        {"shelf": shelf, "vec": vec_str, "limit": k * 4}
    ).fetchall()

    # Access columns by name: r.title, r.page, r.text, r.vec_sim
    return [{"title": r.title, "score": float(r.vec_sim)} for r in rows]
Session lifetime rule Open a short session per DB read. Never hold one session open across a long-running generator (like an SSE stream) — it ties up a database connection for the entire stream lifetime, which starves other requests. Open, read, close, sleep, repeat.
⚡ Transaction safety
Never put :: immediately after a named bind in text()
SQLAlchemy parses :name as a bind — :name::type confuses the parser; Postgres errors

SQLAlchemy's text() treats :name as a bind placeholder. Writing :vec::vector leaves the bind ambiguously parsed; Postgres then sees a syntax error at or near ":". This error appears in the Postgres service logs in CI, not in the Python traceback — so it looks like a different test is failing when the real cause is one SQL call further up the stack.

❌ Broken — Postgres syntax error
session.execute(text("""
    SELECT 1 - (vec <=> :vec::vector)
    FROM library_pages
    ORDER BY vec <=> :vec::vector
"""), {"vec": vec_str})
# CI Postgres log: syntax error at or near ":"
# Adaptive tests die on FK — looks unrelated
✓ Fixed — CAST() keeps bind clean
session.execute(text("""
    SELECT 1 - (vec <=> CAST(:vec AS vector))
    FROM library_pages
    ORDER BY vec <=> CAST(:vec AS vector)
"""), {"vec": vec_str})
# :vec is a normal bind, CAST is SQL
Rule In SQLAlchemy text(), cast a bound value with CAST(:bind AS type), never :bind::type. The Postgres :: shorthand works on literals, not placeholders.
Spotting it in CI Check the Postgres Docker service logs in the GitHub Actions dump, not just the pytest output. Look for syntax error at or near ":" occurring during the test run — FK violations and assertion errors in other tests can be downstream of this one broken SQL call.
SAVEPOINT — safe fallback without destroying the caller's transaction
Use session.begin_nested() when a sub-query might fail in a shared session

When a SQL statement errors, Postgres aborts the whole transaction. A full session.rollback() exits the abort state but also rolls back every uncommitted write the caller made in the same session — seeded rows, linked records, SET LOCAL app.tenant_id (RLS GUC). This triggers a cascade of apparently unrelated test failures.

Real cascade from one bad rollback: vector query errors → session.rollback() → coverage seeds gone → grill_items FK fails → SET LOCAL app.tenant_id cleared → RLS off → tenant B sees tenant A's rows. One rollback caused 28 test failures across 4 files.
❌ Before — recovers Postgres, destroys caller
try:
    candidates = session.execute(
        text("SELECT ... <=> :vec::vector ..."),
        {"vec": vec_str}
    ).fetchall()
except Exception:
    session.rollback()
    # BAD: wipes caller's seeds,
    # clears SET LOCAL tenant GUC,
    # lexical fallback runs with no tenant
✓ After — SAVEPOINT isolates the failure
candidates = []
try:
    with session.begin_nested():   # = SAVEPOINT
        candidates = session.execute(
            text("SELECT ... CAST(:vec AS vector) ..."),
            {"vec": vec_str}
        ).fetchall()
except Exception:
    candidates = []
    # outer session intact:
    # seeds, GUC, RLS all still live

if candidates:
    return hybrid_rank(candidates)
# lexical fallback on same live session
Rule Fallback logic after a SQL error belongs in with session.begin_nested():, not a bare except Exception: session.rollback(), whenever the session is shared with the caller.
Schema cutover: dual-write the new column in ingest AND in test fixtures
Migration backfills existing rows — new writes need updating too

When you add a typed column (e.g. embedding_vec vector(384)) alongside a legacy column (embedding jsonb), the migration backfills existing rows only. Every ingest path and test fixture that only writes the old column leaves the new column NULL — and any query filtering embedding_vec IS NOT NULL returns zero results.

❌ Before — new column stays NULL
session.execute(text("""
    INSERT INTO library_pages
      (..., embedding)
    VALUES
      (..., CAST(:e AS jsonb))
"""), {"e": json.dumps(vec)})

# test mock — wrong dimensions:
monkeypatch.setattr(
    embed_texts,
    lambda _: [[0.0, 1.0]]  # 2-d, not 384
)
✓ After — dual-write both columns
vec_str = "[" + ",".join(str(x) for x in vec) + "]"

    INSERT INTO library_pages
      (..., embedding, embedding_vec)
    VALUES
      (..., CAST(:e AS jsonb),
            CAST(:v AS vector))
"""), {"e": json.dumps(vec), "v": vec_str})

_VEC_DIM = 384
def _pad(values):

asyncio thread safety
Cross-thread queue writes — call_soon_threadsafe
When background worker threads need to put data onto the main event loop's queue

asyncio.Queue is NOT thread-safe. If you put items onto it from a different thread than the one running its event loop, you'll get race conditions or crashes.

❌ Wrong — called from worker thread
def on_step(step):
    queue.put_nowait(step)
    # WRONG if on_step runs on a
    # different thread than the queue
✓ Correct — bounced to main loop
def on_step(step):
    main_loop.call_soon_threadsafe(
        queue.put_nowait, step
    )
    # schedules the put on the right
    # event loop, thread-safely

When this comes up: When you run an async task on a dedicated worker thread (e.g. to get subprocess spawning capability) but need to feed results back to the main request's event loop. The worker thread calls call_soon_threadsafe to safely hand data back.

DriverHandle — worker thread with its own event loop
The pattern in app/thread_bridge.py: ProactorEventLoop + contextvars + concurrent.futures

When the main ASGI event loop can't spawn subprocesses (SelectorEventLoop), you move the work to a dedicated thread that creates a fresh ProactorEventLoop. Two bridges are needed: threading.Event to signal readiness, and concurrent.futures.Future to return the result back to the main loop.

python — DriverHandle (app/thread_bridge.py)
import asyncio, threading, concurrent.futures, contextvars

class DriverHandle:
    def __init__(self, coro_factory):
        self._loop = asyncio.new_event_loop()        # ProactorEventLoop on Windows
        self._result_future = concurrent.futures.Future()
        self._task = None
        ready = threading.Event()
        ctx = contextvars.copy_context()  # ← copies billing_mode and all other request ctx

        def _run():
            asyncio.set_event_loop(self._loop)
            async def _runner():
                self._task = asyncio.current_task()
                ready.set()                          # signal: task is alive
                return await coro_factory()
            try:
                result = ctx.run(self._loop.run_until_complete, _runner())
            except BaseException as e:
                self._result_future.set_exception(e)
            else:
                self._result_future.set_result(result)
            finally:
                self._loop.close()

        self._thread = threading.Thread(target=_run, daemon=True)
        self._thread.start()
        ready.wait()                                 # block until task is running

    def cancel(self):
        self._loop.call_soon_threadsafe(self._task.cancel)

    async def result(self):
        return await asyncio.wrap_future(self._result_future)

Why contextvars.copy_context()? Python context variables (like billing_mode set by request middleware) are scoped to the current task/thread. New threads start with an empty context. Without ctx.run(...), the billing guard on the worker thread would fire incorrectly — blocking every LLM call with "out-of-request metered spend".

Why concurrent.futures.Future not asyncio.Future? An asyncio.Future is bound to a specific event loop. concurrent.futures.Future is loop-agnostic — the worker sets the result; the main loop awaits it via asyncio.wrap_future().

Error Boundary — exact code from this project

Error Boundaries are the only thing that requires a class component. They catch render errors in their subtree and show a fallback instead of a blank screen.

tsx — the real file
import { Component, type ReactNode } from "react"

interface Props { children: ReactNode; name?: string }
interface State { hasError: boolean; error: Error | null }

export class ErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false, error: null }

  static getDerivedStateFromError(error: Error): State {
    return { hasError: true, error }
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error(`[ErrorBoundary: ${this.props.name}]`, error, info)
  }

  render() {
    if (this.state.hasError) {
      return (
        <div>
          <p>Something went wrong.</p>
          <p>{this.state.error?.message}</p>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Retry
          </button>
        </div>
      )
    }
    return this.props.children
  }
}

// <ErrorBoundary name="Interview Panel">
//   <InterviewCard />
// </ErrorBoundary>

    <form onSubmit={handleSubmit}>
      {state.status === "loading" && <span>Saving...</span>}
      {state.status === "error"   && <span>{state.error}</span>}
      <button disabled={state.status === "loading"}>Create</button>
    </form>
  )
}

vs useState: use useReducer when state transitions have names (submit, success, error, reset) and when multiple fields always change together. Use multiple useState calls when fields are independent.

React.memo — prevent re-rendering when props haven't changed
Pair with useCallback — memo only helps if the props are stable
tsx
import { memo } from "react"

// Without memo: re-renders whenever PARENT re-renders, even if item didn't change
// With memo: only re-renders when its own props change
const ItemCard = memo(function ItemCard({ item, onSelect }) {
  console.log("ItemCard rendered for", item.id)
  return (
    <div onClick={() => onSelect(item)}>
      {item.title}
    </div>
  )
})

// This only works if onSelect is stable (useCallback in parent!)
// If parent passes a new function object every render,
// memo does nothing — the prop changed.
function Parent({ items }) {
  const handleSelect = useCallback((item) => {
    setSelected(item.id)
  }, [])   // stable — no deps that change

  return items.map(item =>
    <ItemCard key={item.id} item={item} onSelect={handleSelect} />
  )
}

The chain: React.memo on the child + useCallback on the parent's handlers + useMemo on computed data = avoid unnecessary re-renders throughout the tree.

Why fetch() + ReadableStream instead of native EventSource

The browser's native EventSource API cannot send custom HTTP headers. This app's API requires Authorization: Bearer <token> and X-Tenant-Id: <uuid> on every request — headers that EventSource cannot set.

❌ EventSource — no custom headers
const es = new EventSource("/api/stream")
// Can't set Authorization header
// → 401 Unauthorized
✓ fetch() + manual SSE parse
const res = await fetch("/api/stream", {
  headers: authHeaders()   // includes token
})
const reader = res.body!.getReader()
// Parse SSE lines manually
Also don't put tokens in query strings /api/stream?token=abc123 — tokens in URLs appear in proxy logs, browser history, and server access logs. Always use headers.
Required SSE response headers
python — FastAPI StreamingResponse
return StreamingResponse(
    _stream_events(tenant_id, deliverable_id, since),
    media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache",     # prevent response caching
        "X-Accel-Buffering": "no",       # tell nginx NOT to buffer
    }
)

Why X-Accel-Buffering: no: nginx by default buffers text/event-stream responses, which silently turns streaming into "everything arrives at once" — exactly the problem SSE is supposed to fix. This header tells nginx to pass chunks through immediately.

🔎 Hybrid vector search pattern
Vector pre-filter + lexical reranking
The exact pattern in library_search.py

The problem with pure vector search: returns semantically similar results, but might miss exact keyword matches. Pure lexical (keyword): misses paraphrasing. Hybrid: uses vector to fetch a wide candidate set, then lexical scoring to rerank the best ones.

python — the full pattern
def search_shelf(session, shelf, query, k=5):
    try:
        # 1. Embed the query
        qv = embed_texts([query])[0]
        vec_str = "[" + ",".join(str(x) for x in qv) + "]"

        # 2. Vector pre-filter: SAVEPOINT isolates failure from caller's session.
        #    A bare session.rollback() would wipe seeds + SET LOCAL tenant GUC.
        with session.begin_nested():
            candidates = session.execute(text("""
                SELECT lp.doc_id, ld.title, lp.page, lp.text,
                       1 - (lp.embedding_vec <=> CAST(:vec AS vector)) AS vec_sim
                FROM library_pages lp JOIN library_docs ld ON ld.id = lp.doc_id
                WHERE ld.shelf = :shelf AND ld.status = 'ready'
                  AND lp.embedding_vec IS NOT NULL
                ORDER BY lp.embedding_vec <=> CAST(:vec AS vector)
                LIMIT :limit
            """), {"shelf": shelf, "vec": vec_str, "limit": k * 4}).fetchall()

        if candidates:
            # 3. Rerank with hybrid score:
            #    60% vector similarity + 40% lexical (BM25-like keyword score)
            scored = sorted(
                [{"title": r.title, "page": r.page, "excerpt": r.text[:800],
                  "score": round(0.6 * float(r.vec_sim)
                                 + 0.4 * score_page(query, r.text), 4)}
                 for r in candidates],
                key=lambda x: -x["score"]
            )
            return [r for r in scored[:k] if r["score"] > 0]

    except Exception:   # vector path failed — SAVEPOINT rolled back, outer session intact
        candidates = []

    # 4. Lexical-only fallback (same live session — safe because SAVEPOINT, not rollback)
    rows = session.execute(text("""
        SELECT ld.title, lp.page, lp.text
        FROM library_pages lp JOIN library_docs ld ON ld.id = lp.doc_id
        WHERE ld.shelf = :shelf AND ld.status = 'ready'
    """), {"shelf": shelf}).fetchall()

    scored = sorted([{"title": r.title, "page": r.page, "excerpt": r.text[:800],
                      "score": round(score_page(query, r.text), 4)}
                     for r in rows], key=lambda x: -x["score"])
    return [r for r in scored[:k] if r["score"] > 0]

Key decisions:

  • k * 4 candidates: fetch 20 if you want top 5. The vector filter is approximate — lexical reranking can change the order significantly.
  • 60/40 split: tunable. More weight on vector = more semantic. More on lexical = more keyword-exact.
  • except Exception: pass: if pgvector isn't enabled in prod yet, fall through to lexical. Never hard-fail on missing extension.

The field inside every JWT that says how the user proved their identity

Every Supabase JWT has an amr field recording how the user authenticated. The app checks this to ensure users proved identity with a verified method — not just a password, which doesn't confirm email ownership.

Prompt caching — the financial math
Why adding cache_control to system prompts can save ~90% on repeated calls

Anthropic caches system prompts for 5 minutes. Cache reads cost approximately 10% of the normal input token price.

❌ Before — full price every call
response = client.messages.create(
    system=SYSTEM_PROMPT,
    ...
)
✓ After — 10% on cache hits
response = client.messages.create(
    system=[{
        "type": "text",
        "text": SYSTEM_PROMPT,
        "cache_control": {"type": "ephemeral"}
    }],
    ...
)
math — 100 calls in 5 minutes
# Without caching: 100 calls × 100% = 10,000 units of cost
# With caching:
#   Call 1: 100%  (cache miss — creates the cache)
#   Calls 2–100: 10% each (cache hits)
#   Total: 100% + (99 × 10%) = 100% + 990% = 1,090 units
#   Saving: 10,000 → 1,090 = about 89% reduction

# Cache TTL: 5 minutes. If no new eligible request
# arrives within 5 min, the next call is a miss again.
This project Applied cache_control to all 14 system prompt calls in llm.py. The system prompt doesn't change between calls, so every call after the first (within 5 min) is a cache hit.

🤖 LLM & Agent SDK
Agent SDK requires system_prompt as a string — never a list
Metered Messages API and Claude Agent SDK have different shapes for the system field

The Messages API accepts system=[{"type": "text", "text": "..."}] (a list of content blocks). The Claude Agent SDK (ClaudeAgentOptions) passes this as --system-prompt to the CLI, which expects a plain string. Passing a list causes 'list' object has no attribute 'get' — auth is not the problem.

❌ Passes Messages-API list straight through

# kwargs["system"] is often:
# [{"type": "text", "text": "You are...", "cache_control": {...}}]
# → system_prompt is a list
# → SDK does .get(...) on it → AttributeError
✓ Flatten to string before passing to SDK
def _system_prompt_for_cli(system) -> str:
    if isinstance(system, str):
        return system
    if isinstance(system, list):
        return "\n\n".join(
            block["text"]
            for block in system
            if block.get("type") == "text"
        )
    return ""

system_prompt = _system_prompt_for_cli(kwargs.get("system", ""))
